# Native mobile-only detector (detector-refactor)

KineSync remains on Expo SDK 58, React Native 0.88, and WebView 14. No new runtime dependencies or SDK migration are required.

In iOS and Android Mobile-Only mode, a temporary Spotify WebView reuses the existing login cookies and captures a verified browser bearer, client token, Dealer route, and observer registration destination. Verification requires a non-anonymous token response or the successful account-scoped observer response for that exact bearer. Anonymous/unverified request headers never start the detector. Onboarding and the settings sign-in WebView retain their existing flow.

The app opens its own native Dealer WebSocket and registers a new hidden, non-playing observer against its own connection ID. After registration supplies recognizable track state (or the narrowly recognized idle envelope described below), the closed WebView unmounts. Dealer messages then provide track changes, pause/resume, seeks, device identity, and timestamped position anchors. Browser playback messages never populate this clock. No 250 ms polling, repeated registration snapshots, or audio-device creation/state writes are introduced.

## Lyrics timing

Anchors are projected once to local packet time before entering the existing playback store. The store keeps its monotonic anchors, 1000 ms diagnostic snapshot and separate UI interpolation, including its 80 ms deadband for ordinary playing corrections. Pause, resume, and seek anchors retain existing handling. Duplicate anchors are dropped. Within a known device/session, older source timestamps cannot overwrite newer events. Known device/session handoffs reset the ordering fence. Conflicting registration snapshots cannot undo a Dealer handoff received while registration is in flight. Track identity uses the authoritative Spotify URI rather than title/artist strings, so catalog enrichment does not reset lyrics.

When a valid same-snapshot server/player timestamp pair is present, projection uses its relative age plus elapsed local monotonic time from original receipt. Missing or invalid pairs retain the legacy assumption that source and phone wall clocks agree. It provides no claimed absolute speaker accuracy or calibrated audio offset. Watch for drift/late pauses on an actual iPhone. Synthetic timing tests cannot establish audible alignment.

## Login and lifecycle

Credentials and internal connection routes remain in detector memory. The verified Spotify token also uses the app's existing SecureStore-backed mobile lyrics settings for catalog/lyrics lookups. Known expiry schedules a session refresh. Opaque tokens are renewed conservatively after 45 minutes. A 401 requests fresh browser capture. A 403 enters an explicit account-review/reconnect state with no automatic loop. A 429 retains a shared Retry-After deadline across lifecycle, credentials, renderer resync and manual retry. Ordinary failures use five exponential jittered retries (nominally 2/4/8/16/30 seconds), then one attempt per 60 seconds. A 15-second heartbeat has a 45-second valid-contact watchdog. Only 60 seconds of continuous healthy observation resets the retry budget.

Backgrounding closes the native connection and returning reconnects using the captured session when valid. Control Center's transient inactive state does not deliberately stop observation. Changing to desktop mode disables the detector. Tour entry/disposal and logout suppress queued state/auth/catalog callbacks. Logout also mounts a temporary Accounts logout WebView so shared cookies are cleared even if the player was already unmounted.

Artist enrichment resolves the exact Spotify track GID through the captured spclient session's `/metadata/4/track` endpoint. Connect snapshots can omit artist names. Lyrics searches wait until an artist is available. Metadata is cached and simultaneous requests are deduplicated. Failures expose the HTTP status in diagnostics and the lyrics status. This path does not require the public Spotify Web API token scopes.

Playback controls send gzip JSON commands to `/connect-state/v1/player/command/from/{observer}/to/{active-device}` using the native connection ID. Pause/resume, previous/next, and seek target the device reported by Dealer without mounting the browser. Acknowledgments never synthesize clock anchors. Only subsequent device state updates change playback. Commands are serialized and never automatically retried. Server errors are surfaced to the user. Account/device restrictions can still reject a command. The explicit Spotify browser remains available on demand.

Android also enables the native detector. Android session capture uses the existing desktop Chrome user agent and keeps its bootstrap surface in the viewport until native registration is ready. A bounded startup discovery registers Spotify's already-created Connect observer once, without reading/polling its playback state or creating a playback device. This captures the registration route even when Android defers registration until a local playback action. Both platforms use bounded, single-flight credential probes and same-document page lifecycle guards.

The Android APK workflow has a manual `development` variant. It builds the Debug development client using the release signing certificate and the existing package identity, allowing a certificate-checked `adb install -r` upgrade to preserve shared WebView cookies and stored settings. Subsequent JavaScript changes load through Metro. Never uninstall the existing app to resolve a signature mismatch when preserving its login.

On Android 7 (API 24/25), SDK 58's development launcher references `java.time.Duration` before JavaScript starts. Expo Modules v2 also references `java.nio.file.Path` while initializing its type converters. The Android prebuild plugin enables core library desugaring with `desugar_jdk_libs_nio` 2.1.5 to backport both API families. The standard flavor omits NIO: its missing `Path` class prevents the v2 registry from installing, which surfaces in JavaScript as `Cannot find native module 'ExpoSQLite'` even though SQLite is linked. The plugin also migrates an existing standard-flavor dependency when prebuild runs again. See [Google's desugaring configurations](https://github.com/google/desugar_jdk_libs/blob/master/CHANGELOG.md#version-200-2022-09-16) and [Android's Java API desugaring documentation](https://developer.android.com/studio/write/java8-support). `npm run test:android-compat` checks the migration and repeated prebuilds. Rebuild the native app after changing the backport, Metro alone cannot repair an installed binary. SDK 58 and the minimum Android API remain unchanged. Manual APK builds can select a single native architecture. `x86` matches the existing BlueStacks instance, while the default remains universal.

Protocol references: [Spotcontrol metadata implementation](https://github.com/mcMineyC/spotcontrol/blob/ec66eae39fe5/spclient/metadata.go) and [Spotcontrol spclient command documentation](https://pkg.go.dev/github.com/mcMineyC/spotcontrol/spclient). These internal endpoints must still be verified against the user's actual Spotify session. Mocked regression tests verify our routing and handling, not Spotify's acceptance.

## Reconnect health and control safety

`SpotifyDetector.health` publishes typed native observation health through `spotify-connection-store`. It never overwrites bridge `connectionStatus` or chooses a playback source. The main-player strip remains visible for native mobile playback with empty lyrics, artwork-only views and a closed browser. It distinguishes disconnected/connecting, restoring observation, offline, session renewal/sign-in, account denial, shared cooldown, healthy observation without an active device, and command reconciliation. It has no countdown or frame timer. Native health is hidden while the bridge or the tour owns playback.

Controls require current socket/connection-ID registration and a recognizable current-generation state, an available unrestricted target, active app state, a non-expired token and no pending/confirming command. A new connection ID revokes that proof and cancels old requests immediately. Cached foreground playback is display-only. Transport buttons, seek gestures and queued seek finalization are disabled. Host handlers also guard lyric/credit timestamps, previous-track restart, accessibility and imperative commands before any optimistic anchor mutation.

Recovery owns one socket, one registration, one retry and bounded renewal/command work. WS open, first ID, registration including body and first recognizable state each have a 10-second phase bound. Detachment precedes best-effort native close. Fetch/body callers settle on cancellation/deadline even if the transport ignores abort. Valid idle state certifies observation without inventing a track or reusing a cached device. Malformed frames cannot keep liveness alive.

A command is never queued or replayed. Toggle resolves to pause/resume from current observed state at dispatch. A definite HTTP rejection is distinct from the typed unknown outcome after response loss/cancellation. A stale-target 404 restores observation only. Accepted commands use authoritative state on either side of HTTP settlement. A resulting pause/resume/seek observation or a newer track/session/target can arrive during the POST and supersede the bound intent without disconnecting the healthy observer. An unrelated unchanged toggle state or an older rejected anchor is not positive command confirmation. Absent confirmation for five seconds causes one non-playing observer PUT on the same socket/ID, never a second playback POST. It neither increments transport backoff nor labels the socket failed. Only an actual failure/deadline of that reconciliation enters transport recovery. Generation/ID/target/track/session bindings and local command ownership prevent old completion from clearing a newer command. New state replaces pending confirmation, including a target/track handoff or a no-op skip at context end.

The authentication document runs at most two probes per episode, separated by two seconds, each bounded to 15 seconds including its body. The native renewal episode has a 45-second ceiling. Network/timeout failures return to bounded retry. Explicit anonymous/denied auth and repeated 401 of fresh credentials require sign-in. Pagehide cancels ownership. Pageshow starts one fresh epoch, and old bodies cannot emit credentials. Hidden bootstrap is unmounted during background, offline, cooldown, denial or retry wait. Explicit sign-in starts auth rather than repeatedly registering a forbidden observer.

### Reachability and installed builds

No new package or native dependency is added. The adapter feature-detects an **already installed** ExpoNetwork native module through the existing Expo Modules runtime. This repository does not currently declare expo-network, so ordinary existing builds normally report `unknown`. They still recover through bounded real WebSocket/HTTP attempts. They cannot promise an immediate airplane-mode/offline banner from native network events. A module-provided explicit offline hint suppresses recurring work. Online is debounced for 500 ms. Unknown and online are hints, never readiness proof. Captive portals/DNS/TLS still use deadlines and backoff.

Adding expo-network later would require installing the SDK-compatible package and rebuilding the iOS/Android native app. Metro/OTA alone cannot install that native module. That dependency/build change is intentionally not assumed by this JavaScript implementation. The adapter tests cover module absence, native events, stale initial queries and disposal.

`npm run test:spotify-recovery` executes the actual detector/bootstrap acceptance matrix with injected timers, wall/monotonic clocks, seeded randomness, fetch/body/socket semantics and lifecycle/reachability/callback inputs. It also renders the actual status strip and checks adapter behavior. `check-playback-performance.cjs` exercises production-transformed disabled seek worklets. These checks establish specified transitions and exact no-playback-replay counts, not behavior of the user's installed phone or Spotify's internal endpoints. Reconnect-specific phone validation and independent review remain required.


## Correctness review follow-up (after 8decd30)

Command effects and transport readiness have separate ownership. A positive, ordered current-authority observation can settle or supersede an intent before its successful HTTP response. Next/previous track advances and session/target handoffs are expected supersession, not connection loss. Toggle compares the explicit pause/resume result. Seek uses observed agreement within one second of the requested absolute position for confirmation only (no playback anchor/projection change). This is observational agreement, not a claim that the command caused an independently occurring change. HTTP response loss still produces a typed unknown outcome. Fresh usable observation can remain authoritative without replaying the intent or reconnecting a healthy socket.

An unconfirmed/no-op action waits five seconds and reconciles through one bounded non-playing observer PUT on the existing socket/connection ID. No-op reconciliation retains the generation and transport retry budget and can accept unchanged current observer state without inventing a track change. Older discarded Dealer anchors alone cannot positively confirm a command. Failed reconciliation uses the existing bounded failure path. Confirmation deadlines are installed before health publication and checked by ownership, so synchronous positive observation cannot resurrect an already resolved deadline.

Connection creation is guarded across the entire synchronous attempt, including the socket factory. Connecting health is published after socket ownership, handlers and timers exist. Synchronous health reentry coalesces or cancels the attempt without creating an orphan socket. Captured Dealer URLs are normalized before comparison: access_token and the fragment are removed, remaining query arguments are sorted and preserved. The actual verified bearer is added when opening the native socket. Browser token-query-only changes do not rotate observation authority. Genuine host/path or verified credential changes still do.

### Bootstrap episode ownership (existing behavior verified, not made unbounded)

Successful token capture deliberately exhausts that document's probe allowance (`attempts=2`). Calling `window.__probeToken` or reinjecting the script cannot start an unbounded new episode. The native host's `sessionNeeded` callback **increments browserRun/browserGeneration on every renewal request**, even when sessionNeeded is already true. The WebView key therefore changes, installing a fresh script/epoch in a fresh document. Old keyed document messages are rejected. Actual host lifecycle tests verify both remounts and rejection of obsolete callbacks on iOS/Android in production/development.

Ordinary two-probe exhaustion leaves passive verified observer-response capture available in that document. Pagehide or the whole-episode deadline parks verified credential forwarding. Only the intended pageshow restart or a host document remount re-enables a bounded episode. Tests execute the actual script for success/reinjection, ordinary exhaustion plus passive capture, forced whole-episode expiry with stale passive responses, pageshow and a fresh host document. No new bootstrap restart API or perpetual probe loop was added.

### No-device protocol boundary

An arbitrary empty/malformed 200 body does **not** establish readiness. Empty objects/arrays, empty or array player_state, playing-without-track, malformed track identities and idle-looking data nested under arbitrary keys are rejected and follow the bounded first-state deadline. The synthetic idle fixture `{player_state:{is_paused:true}}` (also explicit is_playing=false) is recognized only through known envelopes, without a claimed active device or track. Its use in tests does not prove Spotify emits that exact no-device shape. Capture and validate actual idle/no-device responses on phone before widening this parser or claiming that case device-verified. Authentication bearer verification and native playback readiness remain distinct checks.

Review regressions run within `npm run test:spotify-recovery`. For an intentional negative comparison, `SPOTIFY_RECOVERY_BASELINE=8decd30 node scripts/check-spotify-recovery.mjs` bundles the actual prior client through a git-show loader and runs only review cases. A nonzero result reproduces the missing race protections. It is not an acceptance pass. Current-source tests require exact one POST, no reconnect/extra PUT for positive in-flight results, one PUT for an unconfirmed no-op, unchanged retry budget, reentrant cancellation cleanup and token-query-only stability.
