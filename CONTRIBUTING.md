# Contributing to KineSync

Contributions are welcome in the mobile app, Desktop Bridge, documentation, accessibility, lyric parsing, and performance tooling. Participation is governed by the [Code of Conduct](CODE_OF_CONDUCT.md).

## Before starting

Search [existing issues](https://github.com/Kineticron/KineSync/issues) and pull requests. For substantial features or architectural changes, open an issue describing the problem and proposed approach before implementing it. Small fixes can go directly to a pull request. Report vulnerabilities privately through [SECURITY.md](SECURITY.md).

Fork the repository, create a branch, and follow [SETUP.md](SETUP.md). Use Node.js 22 and `npm ci` in each component. Commit lockfile changes when dependencies change. A fork does not need production signing secrets to run the JavaScript checks. Native features need a native build. Expo Go alone is insufficient.

## Checks

Run repository checks from the root:

```sh
node scripts/check-repository.cjs
node scripts/release-version.js
```

For Desktop Bridge changes:

```sh
cd DesktopBridge
npm ci
npm run lint
npm test
```

For mobile changes:

```sh
cd ExpoLyrics
npm ci
npm run typecheck
npm run lint
npm test
```

`npm test` runs the deterministic mobile regression suite without Spotify credentials or an emulator. Performance timing is a separate check: use `npm run test:performance` locally on an otherwise idle machine. Shared CI runner timings are not used as speedup gates. [Performance results and reproduction](ExpoLyrics/docs/performance-results.md) describe device capture and release-build requirements.

The **CI / Repository**, **CI / Desktop**, and **CI / Mobile** jobs run on pull requests. Native packaging has separate workflows and requires platform toolchains. Unit checks do not prove that an APK or IPA works on a device.

## Changes and validation

- Keep changes focused and match the surrounding code style. Avoid unrelated formatting or generated native directories.
- Include a regression test for behavior changes where practical. Describe manual checks and unavailable platforms in the PR.
- For playback or lyric rendering, test seeks, pauses, track changes, background/foreground transitions, overlapping vocals, and manual scrolling. Attach before/after screenshots or recordings for visual changes.
- For performance changes, use identical baseline and optimized release workloads. Record device, renderer, display rate, warmup, duration, and raw data. Distinguish lookup speed from whole-app FPS and physical energy use.
- Never commit account tokens, cookies, pairing keys, signing keys, or personal diagnostics. Sanitized fixtures should not contain provider credentials or copyrighted lyric collections.

## Generated files and architecture

Desktop lyric providers live in `DesktopBridge/src/lyrics/parts/` and share a VM context. Top-level names must be unique across parts. The mobile service at `ExpoLyrics/lib/mobile-lyrics-service.js` is a portable bundled copy of the desktop parts, with runtime adapters. No regeneration command is currently shipped: keep matching provider changes aligned in both implementations and run their regression tests.

When changing a WebView entry or its styles, rebuild the corresponding tracked bundle from `ExpoLyrics`:

```sh
npm run build:spicy-webview
npm run build:amll-webview
```

Review the generated diff and include it in the same PR. Native `android/` and `ios/` directories are generated by Expo prebuild. Tracked native modules, widget sources, and config plugins are the source of truth. See [architecture](docs/architecture.md) and [renderer notes](ExpoLyrics/docs/lyrics-renderers.md).

## Localization and text handling

The interface is primarily English. Translation target languages are separate from UI localization and from pronunciation/romanization. Native speakers should review localized text in context. Machine-generated output alone is not sufficient validation.

Test mixed scripts, punctuation, right-to-left layout, combining marks, and scripts without whitespace word boundaries. Preserve provider timing and word-join information. Do not animate individual Unicode code points as though each were an independent displayed glyph. Explain the languages and examples used to validate a parsing or layout change.

## Pull requests

Describe the problem, resulting behavior, and validation using the PR template. Link related issues and disclose material limitations. There is no required commit-prefix convention or CLA. Contributions retain the license of the component they modify. Preserve upstream notices when copying or adapting code. Maintainers may ask for changes before merging, and response times depend on volunteer availability.
