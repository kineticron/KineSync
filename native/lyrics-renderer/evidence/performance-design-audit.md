# Native renderer performance and design audit

Audited 2026-11-15 on `rust-renderer-spike`, starting at `44a7d7c` after `git pull --ff-only` reported up to date. The two existing local commits were preserved. Scope is the Rust crate and its iOS Swift owner. The unchanged Skia wrappers and native view were consulted as the behavior reference.

Ranking below is engineering priority from code inspection, not a measured iPhone cost ranking. No new phone timing, battery, or scanout results were collected. Only the two resource caching changes were implemented. No shader, timing constant, scroll behavior, ABI, or Swift code changed.

## Ranked findings

1. **Why render at the maximum requested refresh rate for all playback?**
   `KineSyncRustLyricsModule.swift:514-557` treats positive-rate playback as sufficient reason to keep submitting frames and prefers the screen maximum, capped at 120 Hz. This is a simple way to keep reveals, dots, springs, and scrolling moving. It also keeps doing full scene and GPU work during settled gaps, while manually looking at static rows, and after the final visible animation. The minimum of 30 is a scheduling hint, not a guarantee that static content becomes cheap. Simpler policy: report whether visible pixels are changing and the next time they can change. Stop the display link when settled, arm a cancellable wakeup for the next cue, and use the high refresh hint during visible motion. Playback time must continue independently. Check reveal, priming, dot breathing, outgoing tails, manual scrolling, seeks, and resume before adopting this. Merely testing `animating` is insufficient because continuous word fill also changes pixels.

2. **Why filter the entire surface on every frame?**
   `gpu.rs`, `Filter::encode`, always dispatches a half-resolution downsample, four half-resolution Gaussian passes, and a full-resolution composite. This shares two blur bases across all rows and glow instead of executing a blur for each voice. That is a useful design choice, but it still reads and writes transparent areas, even when the protected band covers most text. Live rendering always supplies blur=true and glow=true. Simpler first step: skip filter work only when neither distance blur nor emission can contribute. Next, dispatch over the union of actual text, subtitle, dot, and footer ink bounds, expanded for both kernel axes and reconstruction taps. Clear old regions when bounds move. Text layout bounds alone are insufficient because glyph overhang, transforms, and glow extend outside them. `UIVisualEffectView` is a backdrop effect and would blur different content. A Metal-specific built-in filter would require interoperability and output validation, so it is not a drop-in simplification.

3. **Why shape cold rows after acquiring a scarce drawable?**
   `ffi.rs:513-590` acquires first, refreshes the clock, then calls `prepare` and `prepare_viewport`. Acquiring first prevents animation sampling from becoming stale during a drawable stall. But `scene.rs:418-890` can then clone lines, shape multiple paragraphs, build glyph scenes and slices, and retire old geometry while holding that drawable. Simpler design: separate immutable row preparation from time-sensitive animation sampling. Prepare near-future geometry before acquire on the existing serial worker, acquire, refresh the clock, then sample and encode. Explicit seeks need a bounded readiness policy if acquisition crosses a cue. Preserve placeholder heights and promotion pixels. Do not simply move the entire current frame calculation before acquire.

4. **Why build diagnostic JSON when nobody requested it?**
   `scene.rs:721-881` always creates face descriptions, formatted attributes, coordinate arrays, word-range arrays, and row/voice JSON, including a deep clone of the lead receipt. `auxiliary.rs`, `Translation::prepare`, builds a similar receipt. This makes evidence collection convenient but puts debug work into cold frame preparation. `ffi.rs:231-255` serializes the whole receipt twice for Swift's size-then-copy request. Simpler alternative: retain minimal typed layout facts and materialize JSON on explicit `copyLayout`, or enable detailed collection for a diagnostic session. Cache the serialized bytes for the two-call copy. Proposed rather than implemented because changing when evidence is available needs a receipt-equivalence test, including already prepared rows, eviction, and subtitles. Silently returning null receipts would break the current debugging contract.

5. **Why scan the whole track repeatedly to rediscover the same playback window?**
   `lib.rs`, `window`, supports overlapping and out-of-source-order lyric starts. Multiple frame helpers call it independently, including scene preparation, scroll commands, interlude lookups, appearance, and drawing. It can perform several source-order scans in a gap. `appearance.rs:61-80` even asks again for each newly promoted future row. These scans exist for correct timing, not visibility. Simpler first step: calculate one immutable playback-window result for a sampled frame and pass it through. Later, precompute sorted timing events and an overlap-safe interval index, with reset on seek. Binary-searching the existing source order would be incorrect. This can matter more than replacing one row drawing loop.

6. **Why walk every row to draw only a few?**
   `timed_scene.rs:313` and `scene.rs`, `frame_prepared_adjusted`, scan all cached row slots before applying viewport rejection. `appearance.rs:67,173` scans all slots during prepare and advance, and `animating` scans again. Paragraph residency is bounded but these arrays still have the full track length. `visible_rows` already uses `partition_point`, which is the simpler built-in tool for ordered row positions. Use a conservative draw range that also includes row cascade offsets, interlude shifts, glyph overhang, and effects. Keep appearance updates over a separate set of resident or transitioning rows. Updating only currently visible rows would lose outgoing spring state and alter future promotion pixels. Row eviction and prefix rebuilding already run mainly when preparation changes, not on every warm frame.

7. **Why rebuild GPU objects whose inputs did not change? Fixed.**
   `Gpu::render_frame` created a view of the same sharp texture each frame. `SurfaceRenderer::render_surface` created another view of the same composite texture and a new surface source bind group. Texture views and bind groups are reusable objects. Commit `760a120` retains sharp and composite views until resize. Commit `10df90c` retains the source bind group and replaces it on resize. The drawable output view still changes with the acquired drawable. Filter bind groups, Gaussian weights, and scratch textures were already cached. The new GPU regression compares cached bindings with fresh bindings byte for byte across repeated frames, growth, and shrink.

8. **Why hand-build momentum and rubber banding?**
   Swift's `manualPan` samples UIKit translation and velocity, then Rust's `motion.rs:226-378` implements drag bounds, deceleration, overscroll, and rebound. This keeps one Rust offset shared by rendering, hit testing, and follow handoff. But it duplicates native scrolling behavior and tuning, and queue delays affect input responsiveness. Simpler iOS design: a `UIScrollView` owns manual offset, momentum, and bounce, while the Metal view stays viewport-sized and receives the sampled content offset. Keep style-specific automatic follow trajectories and AMLL row cascades unless a separate parity decision replaces them. Define one authoritative offset during the handoff, update content size as row heights become known, and preserve tap/hold arbitration. Replacing everything with `scrollTo` would change the reference's auto-follow motion.

9. **Why hold a global mutex across a whole frame?**
   `ffi.rs:76-105` holds the engine registry lock across drawable acquisition, scene work, GPU submission, and presentation. It protects handles and panic retirement, but unrelated engines cannot make progress. Swift already uses one static serial worker for all owners, so there is currently a second global serialization layer. Simpler Rust design: lock the registry only to obtain a retained per-engine owner, then lock that engine. Preserve destroy ordering, stale handle rejection, and panic retirement. Changing just the Rust mutex will not make iOS owners independent while Swift still shares its worker. Do not remove synchronization solely because today's caller is serial.

10. **Why an intermediate texture and another fullscreen pass?**
    The final surface pass is not a byte copy. `surface.wgsl` converts linear premultiplied output into encoded premultiplied sRGB for Core Animation. `composite.wgsl` also applies protection, glow, and edge fade. Removing the pass without moving those operations changes color and transparency. A plausible simplification is a final render pipeline that directly composites sharp/blur bases, fades edges, and performs surface encoding into the drawable. Keep offscreen readback as an alternate target. This would remove the intermediate composite write and subsequent read, but could also change rounding because the current path quantizes to RGBA8 before surface encoding. Require pixel comparisons, including low alpha and colored pixels. Do not substitute a texture copy command.

11. **Why rebuild pipelines and wait on all GPU work for resize?**
    `Gpu::resize` waits indefinitely and recreates `Filter`, including three shader modules and compute pipelines whose code did not change. Resize really needs new textures, texture bindings, extents, and scale-dependent weights. Split immutable pipelines from size-dependent filter resources and reuse the pipelines. Investigate retiring old resources through queue ownership rather than waiting for the whole device, while respecting surface reconfiguration rules. Resize is occasional, so this ranks below warm-frame waste, but rotation can block new input because it occupies the shared worker.

12. **Why retain several versions of the same row and font state?**
    A prepared voice keeps white and packed plain scenes, a parley layout, word fragments, timed glyph copies, and sometimes an idle Spicy scene. The native engine also keeps source lines alongside the TrackScene copy. Some duplication serves distinct painters and the Spicy cold-to-detailed parity fix. It is not safe to delete those scenes indiscriminately. Simpler ownership: immutable source shared with `Arc`, one reusable glyph-run store feeding the required encodings, and optional detailed state. Avoid reconstructing Spicy idle geometry during promotion. Profile retained bytes before changing representations.

13. **Why are cache limits counts rather than memory budgets?**
    Row geometry is evicted outside a playback neighborhood and the layout cache retains at most three old variants. This limits count, not bytes. A row with many emphasized graphemes or background voices can be much larger than a simple line. Five half-resolution RGBA16F scratch textures plus two RGBA8 full-size textures cost approximately 18 bytes per full-resolution pixel before Vello resources and OS drawables. The 8192 dimension guard is not a memory budget. Simpler policy: a byte budget for retained geometry and GPU extents, plus small count limits. Coordinate allocation failure with surface recreation rather than silently reducing raster scale and changing visuals.

14. **Why serialize and hash the whole source for each layout variant?**
    `scene.rs:1239-1259` allocates JSON for every line, setting, credit, extent, and font hash to compute a cache key. This is track/resize work, not steady frame work. It ensures exact invalidation but repeats unchanged source serialization during rotation. Simpler design: compute a source digest once per accepted packet, then combine it with the small layout settings. Stream serialization into the digest to avoid the temporary byte vector if retaining the existing format. Keep content, translation, timing, font, and style invalidation coverage.

15. **Why wake main and reenter Rust for bookkeeping every frame?**
    `RustOwner.draw` creates worker/main closures and calls `kr_metrics` after each render so main can learn whether animation continues. Full metrics dictionaries and Expo events are already throttled to once per second. The per-frame completion also clears `busy`, checks revisions, and handles drawable retries, so removing it blindly breaks scheduling. Simpler eventual design: keep frame scheduling and settle state with the render owner, return only state changes to main, and sample telemetry separately. Keep bounded in-flight work, fresh timestamps, generation rejection, and inactive shutdown. Do not replace display-synchronized scheduling with a generic repeating timer.

16. **Why does one stalled owner block every other owner and every drag update?**
    The static `RustOwner.worker` serializes rendering, cold layout, copy receipts, gestures, resize, and retirement for all views. It intentionally orders old-owner teardown before remount on the same retained layer. Inputs and anchors use a bounded latest snapshot, which is good. Drag deltas deliberately queue individually to preserve ordering, so they can collect behind slow preparation. Simpler policy: explicit per-layer lifetime ownership with per-owner workers, and combine adjacent drag deltas only within a gesture epoch without crossing anchor, follow, resize, or fling boundaries. Fix the Rust registry lock too. This is an ownership redesign, not a safe queue substitution.

## Allocation and clone inventory

- Warm scene construction: existing allocation-probe tests pass at zero after warmup for their covered cases. This does not include wgpu internals or prove every transition is allocation-free.
- Every GPU frame: command encoders and command buffers, Vello internal recording/submission work, the acquired drawable view, and a submitted-work completion closure. The completion's `Arc` clone shares a counter, it does not deep-copy frame state. Stable sharp/composite views and the surface source bind group are now cached.
- Every Swift frame: worker and main completion closures plus a metrics value. Metrics dictionaries and cross-Expo events are throttled. Queue and driver allocations have not been counted on iOS.
- New or evicted row preparation inside a frame: a deep `Line` clone, scratch one-row vectors and TrackScene, a new LayoutContext, repeated probe/unwrapped/final shaping, cluster width vectors, glyph vectors, normalized coordinate vectors, multiple encoded scenes, diagnostic strings/JSON, word fragments, and timed slices. Spicy builds timed geometry to generate its idle picture even for a plain row, then drops that timed geometry if the row is not detailed.
- Appearance promotion: row voice arrays, WordState arrays, and emphasized-letter springs. These are retained for reuse, not reallocated on every steady frame.
- AMLL retargeting: the trajectory Vec can grow until its small bounded history is warm. Removing its first element moves bounded data. Row delay fills touch the whole track on retarget, while cascade sampling already uses visible ranges. Cloning a `Range<usize>` only copies its endpoints and is not a heap allocation.
- Track/resize: packet parsing, source/settings/credits clones, font context clones, all-source cache-key JSON, footer/dot preparation, GPU texture creation, and filter pipeline recreation. These may delay frames on the same worker but should not be described as unconditional per-frame work.
- Explicit diagnostics: the Swift size-then-copy call currently causes two full serializations. `Fonts::describe` caches font lookup/hash work, but returns cloned face strings for each receipt.

## Simpler built-ins and their limits

Apple provides [display-link refresh hints](https://developer.apple.com/documentation/quartzcore/cadisplaylink/preferredframeraterange) and [UIScrollView](https://developer.apple.com/documentation/uikit/uiscrollview) with [native deceleration](https://developer.apple.com/documentation/uikit/uiscrollview/decelerationrate-swift.property). Those address cadence policy and manual scroll ownership. They do not infer whether this renderer's pixels change or implement its custom automatic lyric trajectories.

[wgpu bind groups](https://wgpu.rs/doc/wgpu/struct.BindGroup.html) are reusable. The pinned Vello 0.12 scene API provides blurred rounded rectangles, not a drop-in arbitrary glyph-mask blur matching this compositing scheme. Replacing the text renderer or Gaussian backend is a separate visual design decision. No dependency update is needed for the implemented caches.
